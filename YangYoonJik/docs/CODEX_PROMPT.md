# 상권나침반 MVP 구현 킥오프

이 작업은 자유로운 설계 작업이 아니다.
현재 저장소에 이미 정의된 프로젝트 하네스와 제품 명세를 그대로 구현하는 작업이다.

임의로 요구사항을 재해석하거나, 더 나은 방법이라는 이유로 아키텍처·데이터 규칙·점수 산식·UI 원칙을 변경하지 마.

---

## 0. 작업 디렉터리 확인

현재 작업 루트가 반드시 다음 프로젝트 루트인지 먼저 확인해라.

C:\Vibecoding\myMap_mk1

다른 디렉터리에서 작업 중이라면 구현을 시작하지 말고 프로젝트 루트를 올바르게 연 뒤 진행해라.

---

## 1. 하네스 우선순위

이 프로젝트에서는 다음 문서가 구현의 단일 기준이다.

우선순위:

1. AGENTS.md
2. SPEC.md
3. docs/DATA_REQUIRED.md
4. 이 킥오프 프롬프트

하위 문서나 현재 프롬프트의 내용이 상위 문서와 충돌하면 반드시 상위 문서를 따라라.

AGENTS.md와 SPEC.md는 구현 대상이 아니라 프로젝트 계약이다.

명시적인 요청 없이 다음 파일을 수정하지 마.

- AGENTS.md
- SPEC.md

문서 내용이 마음에 들지 않거나 다른 구현이 더 적절해 보여도 임의로 변경하지 마.

---

## 2. 구현 전 필수 사전검증

코드를 수정하기 전에 반드시 다음을 수행해라.

1. AGENTS.md 전체를 읽는다.
2. SPEC.md 전체를 읽는다.
3. docs/DATA_REQUIRED.md 전체를 읽는다.
4. 현재 저장소의 파일 및 디렉터리 구조를 확인한다.
5. data/raw 경로에 실제 공공데이터가 존재하는지 확인한다.
6. package.json, Python 환경 파일, 기존 소스가 존재하면 확인한다.
7. VWorld 환경변수 사용 여부를 확인한다.

파일 일부만 검색해서 추정하지 말고 위 핵심 문서는 전체를 읽어라.

사전검증이 끝난 후 내부적으로 다음 항목이 모두 확인되어야 한다.

- 대상 사용자: 예비 창업자
- 초기 지역: 송파구
- 업종: 상위 카테고리 + 하위 세부업종
- 핵심 기능:
  - 1년 성장 가능성
  - 업종 맞춤 상권 추천
  - 위험·과열 상권 경고
- 지도:
  - OpenLayers
  - VWorld WMTS
  - 버블맵
  - 클릭 시 상권 Polygon 강조
- 운영 구조:
  - 정적 프론트엔드
  - 운영 서버 없음
  - 운영 DB 없음
  - 유료 API 없음
- 디자인:
  - 밝은 라이트 테마
  - AI 양산형 UI 금지
  - 한글·영문 브랜드 혼용 금지
  - 애매한 줄바꿈 금지
  - UI 간 겹침 금지

위 항목 중 SPEC.md와 다른 것이 있다면 이 목록이 아니라 SPEC.md를 우선한다.

## 4. 데이터 규칙

실제 원본 공공데이터가 존재하면 반드시 실제 데이터만 사용한다.

기본 데이터 소스와 JOIN 규칙은 SPEC.md를 그대로 따른다.

특히 다음 JOIN 계약을 임의로 변경하지 마.

매출 + 점포:

quarter
+ areaId
+ industryCode

유동인구:

quarter
+ areaId

영역:

areaId

송파구 필터도 SPEC.md의 영역 데이터를 기준으로 수행한다.

---

## 5. 실제 데이터가 없는 경우

data/raw에 필요한 원본 데이터가 없다면 다음 순서로 행동해라.

1. docs/DATA_REQUIRED.md를 확인한다.
2. SPEC.md에 명시된 서울시 공식 공개 경로에서 실제 데이터를 얻을 수 있는지 확인한다.
3. 현재 환경에서 다운로드할 수 있으면 실제 데이터를 다운로드한다.
4. 접근 제한이나 네트워크 제한 때문에 다운로드할 수 없으면 가짜 데이터를 생성하지 않는다.

데이터를 확보하지 못한 경우에도 다음은 구현한다.

- 실제 파일을 읽는 ETL 코드
- 데이터 검증 로직
- JOIN 코드
- 분석 코드
- 프론트엔드
- 빈 상태 UI
- 오류 상태 UI
- 지도 키 없음 상태
- 테스트 가능한 코드 구조

그리고 누락 데이터를 docs/DATA_REQUIRED.md 또는 IMPLEMENTATION_STATUS.md에 정확하게 기록한다.

가짜 데이터로 화면을 그럴듯하게 채우는 것보다 빈 상태가 우선이다.

## 6. 점수 및 분석 규칙

성장점수, 현재 건강도, 위험점수, 추천점수의 계산 방법은 SPEC.md의 산식을 정확하게 구현한다.

정규화 역시 SPEC.md의 다음 원칙을 따른다.

- 5~95 percentile winsorize
- 동일 분기
- 동일 업종
- 송파구 상권 내 percentile rank
- 0~100 점수화

현재 성장 건강도의 가중치:

- 매출 성장: 35%
- 유동인구 성장: 25%
- 점포당 매출 성장: 40%

과열·위험 점수:

- 점포 증가 위험: 30%
- 점포당 매출 감소: 35%
- 폐업 위험: 25%
- 매출 성장 둔화: 10%

추천점수:

추천점수 =
성장 가능성 점수 × 70%
+
안전점수 × 30%

안전점수 =
100 - 과열위험점수

SPEC.md에 이보다 더 상세한 정의가 있으면 SPEC.md를 따른다.

## 7. 미래 성장 모델

미래 예측은 SPEC.md의 기준을 그대로 구현한다.

학습 구조:

t 시점 특징
→
t + 4분기 성장 여부

Target은 SPEC.md에 정의된 성장 조건을 그대로 사용한다.

모델:

RandomForestClassifier

단, 모델 이름만 같게 만들고 검증을 생략하면 안 된다.

반드시 시간순 검증을 수행한다.

---

## 8. 모델 검증 실패 처리

이 항목은 절대 변경하지 마.

SPEC.md의 모델 검증 기준을 충족했을 때만 미래 성장 모델 결과를 사용자에게 노출한다.

검증을 통과하면:

- 1년 성장 가능성 점수를 노출할 수 있다.

검증을 통과하지 못하면:

- growthScore를 미래 예측값으로 노출하지 않는다.
- 가짜 예측값으로 대체하지 않는다.
- 현재 성장 건강도를 미래 성장점수처럼 표현하지 않는다.
- UI에서 "현재 성장 건강도"라는 명칭을 사용한다.
- 미래 예측 데이터가 충분하지 않음을 명확하게 표시한다.

검증되지 않은 숫자에는 "확률"이라는 표현을 사용하지 마.

## 9. 업종 계층

사용자 UI는 상위 카테고리 → 하위 업종 구조를 사용한다.

예:

음식점
- 한식
- 중식
- 일식
- 양식
- 치킨
- 분식
- 패스트푸드

카페·베이커리
- 커피·음료
- 제과점

그 외 카테고리는 SPEC.md 및 category mapping 규칙을 따른다.

서울시 원본 서비스업종코드를 직접 변경하지 않는다.

별도의 category mapping 계층을 사용한다.

상위 카테고리 "전체" 분석 시 하위 업종 점수를 단순 평균하지 않는다.

SPEC.md에서 정의한 대로 원본 데이터를 먼저 합산한 후 파생지표를 다시 계산한다.

## 10. 지도 구현

지도는 반드시 다음 조합을 사용한다.

OpenLayers
+
VWorld WMTS
+
송파구 상권 GeoJSON
+
분석 JSON

VWorld API Key:

VITE_VWORLD_API_KEY

키를 코드에 하드코딩하지 마.

.env.local은 저장소에 커밋하지 않는다.

키가 없어도:

- npm build가 성공해야 한다.
- 애플리케이션이 crash하면 안 된다.
- 지도 영역에서 설정 필요 상태를 명확하게 표시한다.

VWorld 키가 없다는 이유로 OpenStreetMap, Google Maps, Kakao Maps, Naver Maps 등 다른 지도 타일을 임의로 사용하지 마.

## 11. 버블맵

메인 지도 시각화는 버블맵이다.

버블은 상권 중심좌표에 표시한다.

기본 의미:

- 버블 크기 = 성장 관련 점수
- 상태 표현 = 성장 / 주의 / 과열 / 위험
- 버블 클릭 = 해당 상권 Polygon 강조
- 상세 패널 표시
- 업종 변경 시 버블 데이터 재계산/재표시

지도 전체를 무조건 choropleth로 대체하지 마.

Polygon은 선택된 상권의 실제 영역을 확인하는 보조 표현이다.

## 16. 코드 품질

구현 중:

- TypeScript 타입을 명확히 정의한다.
- any 남용을 피한다.
- React 컴포넌트를 과도하게 거대하게 만들지 않는다.
- 데이터 로직과 UI 로직을 분리한다.
- Python 분석 로직을 함수 단위로 분리한다.
- 반복되는 상수를 config로 관리한다.
- 업종 category mapping을 코드 곳곳에 하드코딩하지 않는다.
- 환경변수를 하드코딩하지 않는다.
- 경로를 Windows 절대경로로 소스에 박지 않는다.
- 분석 재실행이 가능하도록 ETL을 재현 가능하게 만든다.

## 17. 테스트 및 완료 조건

구현 완료 전 반드시 가능한 범위에서 다음을 실행한다.

프론트:

npm install
npm run build

package.json에 지원되면:

npm run typecheck
npm run lint

Python:

python -m pytest

ETL 실행 명령이 있다면 실제로 실행한다.

가능하면 생성된 JSON을 검증한다.

최소 검증 항목:

- JSON parse 성공
- areaId 누락 검사
- quarter 누락 검사
- industryCode 누락 검사
- duplicate key 검사
- NaN/Infinity 검사
- 점수 범위 0~100 검사
- 송파구 외 데이터 포함 여부 검사
- Polygon/상권코드 연결 여부 검사

테스트 실패를 숨기지 마.

IMPLEMENTATION_STATUS.md

를 생성한다.

### 구현 완료

## 19. Hard Blocker 처리

다음에 해당할 때만 사용자에게 추가 정보를 요청해라.

- 실제 구현을 진행할 수 없는 필수 파일 부재
- 사용자만 발급할 수 있는 인증정보가 반드시 필요한 단계
- 문서 간 직접적인 모순으로 구현 결과가 달라지는 경우
- 현재 환경 권한상 필요한 명령을 실행할 수 없는 경우

그 외에는 가능한 합리적인 범위에서 문서 기준대로 직접 진행해라.

질문을 최소화하기 위해 요구사항을 임의 변경하는 것은 금지한다.
